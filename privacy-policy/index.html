PRIVACY NOTICE

How MultiPost handles connected-platform data.

Effective date: 28 October 2026. TIGO operates the MultiPost product website and Windows application. This notice explains the data handling for this website, the current TikTok Sandbox reviewer connection, and the separate legacy developer builds that include a Google and YouTube connection.

Contact: for privacy questions, local-data deletion help, or a request concerning support correspondence, email TIGO at ovtom22@gmail.com.

TikTok connection · Local storage · Disconnect and deletion

1. Scope

This notice applies to MultiPost, its product website, and the data handled by a released or testing build when a creator uses a supported platform connection. Platform availability can differ by build, account eligibility, provider approval, and the creator's selected destination. This notice does not replace the privacy terms of Google, YouTube, or another connected platform.

2. Information MultiPost handles

Depending on the features a creator uses, MultiPost can handle the following information:

  • Selected media file paths, file metadata, prepared local delivery variants, cover selections, titles, descriptions, captions, scheduling choices, and publishing settings.
  • Connected-account display names, platform identifiers, connection status, publishing timestamps, remote post or video identifiers, and platform response messages.
  • Access and refresh credentials returned after the creator completes a supported authorization flow.
  • Local app preferences, drafts, job history, and operational log messages.
  • The sender's email address and message content when the sender contacts TIGO by email.

3. Google and YouTube data

The current TikTok reviewer package does not include YouTube. In separate legacy developer builds that include YouTube, MultiPost opens Google's authorization page in the system browser. The creator signs in directly with Google and chooses whether to grant the requested access. MultiPost does not ask for or receive the creator's Google password. The direct Google exchange described here applies to those legacy developer builds; it does not describe an available commercial YouTube release.

The YouTube connection requests these Google OAuth scopes:

  • https://www.googleapis.com/auth/youtube.upload, used to upload the creator-selected video and, where selected, its thumbnail.
  • https://www.googleapis.com/auth/youtube.force-ssl, used because MultiPost can upload a creator-selected caption track.

After authorization, MultiPost uses the returned credentials to identify the connected YouTube channel, upload the video chosen by the creator, upload the selected thumbnail, and upload a caption track when the creator selects one. The YouTube upload can include the video's title, description, privacy setting, and any selected captions. Google and YouTube process data sent to their services under their own terms and privacy policies.

4. TikTok Sandbox connection

When a supported MultiPost build connects to TikTok, sign-in takes place on TikTok's official page. MultiPost does not ask for the creator's TikTok password. The current TikTok reviewer candidate requests user.info.basic to identify the connected creator and video.publish for Direct Post. A TikTok account can have an existing grant that includes additional permission names reported by TikTok, including video.upload. MultiPost records the actual grant returned by TikTok. The current reviewer candidate does not implement TikTok's separate upload-to-inbox or draft-upload feature.

TIGO operates the TikTok authorization service at auth.ilgotic.com on a Scaleway server in Warsaw. The service processes the authorization callback, short-lived sign-in state, and token exchange needed to complete sign-in. When the desktop requests a refresh, the service also processes the refresh credential to forward the refresh request to TikTok. The service processes access and refresh credentials during those exchanges, but its application sign-in state table does not retain creator access or refresh credentials. The TikTok developer client secret is held in protected server configuration and is not included in the desktop reviewer package.

The service keeps short-lived sign-in records containing the state needed to protect and complete an authorization flow, such as a flow identifier, desktop-provided state and challenge values, a hashed one-time ticket, an authorization code after a successful callback, a fixed denial result when applicable, and an expiry value. Redeemed flow records are removed, and expired flow records are removed by service cleanup while the service is operating. This describes logical record expiry and deletion. It is not a guarantee that every infrastructure, disk, journal, backup, or other copy is physically erased within a fixed time.

Routine application access logging is disabled for the authorization service. Hosting, security, and error systems can still process network traffic and connecting IP addresses. TIGO does not currently specify a fixed retention period for those infrastructure records or for support correspondence. To request deletion of support correspondence or information about a particular record, use the contact address above.

5. Local storage and credential protection

MultiPost stores its working records in the current Windows user's application-data folder, normally %APPDATA%\MultiPost. The app database keeps local drafts, job history, connected-account records, and the paths to selected files. The selected source video remains on the creator's computer unless the creator directs MultiPost to send it to a connected platform.

In legacy developer builds with YouTube, access and refresh credentials are stored in the local app database protected with Windows Data Protection API for the current Windows user. Those builds exchange and refresh credentials directly with Google's services. This is a description of that legacy connection, not a claim that every MultiPost build uses the same authorization architecture. The current TikTok reviewer package has no YouTube connection.

For TikTok, the Windows desktop stores connection credentials and protected account metadata in the current Windows user's profile with Windows Data Protection API protection. Display names, connection status, drafts, job history, generated cover frames, and prepared media variants are local working records. The current source does not provide automatic time-based deletion for those local records.

The separate TikTok reviewer package uses %LOCALAPPDATA%\MultiPost TikTok Review\appdata\MultiPost instead of the normal %APPDATA%\MultiPost profile. These are different local profiles. The reviewer package does not import the normal personal MultiPost account, draft, or queue data.

6. How information is used and shared

MultiPost uses the data above to show the selected account, prepare and review a creator-selected post, make the platform request the creator approves, report the platform response, and provide support when contacted. MultiPost does not use YouTube API data to serve advertising or to build an advertising audience.

When the creator connects or publishes, the relevant information is sent to the selected platform under the creator's direction. For the YouTube connection, this can include Google authorization information and the video, thumbnail, captions, title, description, and publishing settings needed by YouTube. If the creator enables an optional AI writing feature, the text supplied for that feature can be sent to the provider selected for that request.

For TikTok Direct Post, MultiPost first retrieves creator information directly from TikTok to show the current creator, permitted audience and interaction choices, and duration limit. After the creator reviews the post and gives consent, the desktop sends the approved caption and settings to TikTok and transfers the selected video directly to TikTok's returned upload address. The TIGO authorization service does not receive the video's bytes in that flow.

The current product website is static and does not include an analytics script, advertising script, payment form, or visitor-account registration.

7. Disconnecting, revocation, and deletion

In legacy developer builds with YouTube, Disconnect clears the local access and refresh credential fields and display name. It does not send a Google revocation request or remove all local account metadata, drafts, history, or cached files. To remove the Google-side authorization, use the connected-app controls in the creator's Google Account. The current TikTok reviewer package does not include this YouTube connection.

A TikTok disconnect clears locally stored access and refresh credential fields and the display name from the current MultiPost profile. It can retain local account metadata, drafts, history, cached media, and other local working records. The current TikTok connection does not send a TikTok provider-revocation request. TikTok-side authorization, privacy controls, and posted content must be managed through the creator's TikTok controls.

To remove local MultiPost data, close the application and remove the %APPDATA%\MultiPost folder. This removes local drafts, history, settings, and stored connection records from that Windows user profile. It does not remove videos, channels, posts, or records held by YouTube or another platform. Those must be managed through the relevant platform account and its privacy controls.

To remove the local TikTok reviewer data, first close the reviewer application, then remove only %LOCALAPPDATA%\MultiPost TikTok Review\appdata\MultiPost. Do not remove the normal personal MultiPost profile when cleaning up the reviewer package. Local deletion does not delete TikTok posts, provider-held records, or the creator's TikTok authorization.

To request deletion of support correspondence held by TIGO, email ovtom22@gmail.com from the address used to contact support and describe the request. In the legacy developer YouTube connection described here, TIGO does not receive the creator's Google credentials through an authorization server; the credentials are stored in the creator's Windows profile and exchanged directly with Google.

8. Security and account responsibility

MultiPost is designed to use official provider authorization pages and to protect locally stored connection credentials with the current Windows user's profile protection. No storage or transmission method is completely secure. Creators should protect their Windows account and connected-platform accounts and should not send passwords, access tokens, developer credentials, or local database files to support.

9. Google policies and changes

Google's handling of data is governed by Google's own policies, including the Google Privacy Policy and the Google API Services User Data Policy. MultiPost may update this notice when the data flow or available features change. The effective date at the top of this page will be updated with the notice.
